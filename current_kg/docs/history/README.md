Kiwi는 [공식 문서](https://github.com/bab2min/kiwipiepy)의 형태소·품사·문자 위치 정보를 활용하는 보조 분석기이며 정답 판정기가 아니다. 실제로 계세요의 분석이나 융합된 -더라에서는 선어말을 확정하기 어려워 보류했다. 높임·형태·기능 분석 전체의 정확성을 보장하지 않으며, Qwen이 잘못 분류한 절 관계·의도·서술어를 모두 고친 것은 아니다.

환경은 프로젝트 전용 `.venv/analysis`에 설치했고 [requirements-analysis.txt](../../experiments/requirements-analysis.txt)에 버전을 고정했다(Kiwi 0.23.1, 모델 0.23.0). 새 환경에서는 `/usr/bin/python3 -m venv --system-site-packages .venv/analysis` 후 `.venv/analysis/bin/python -m pip install -r current_kg/experiments/requirements-analysis.txt`를 사용한다. 자동 분석 및 실험 코드 검사는 이제 `.venv/analysis/bin/python`으로 실행한다. 기존 MD의 과거 `/usr/bin/python3` 실행 기록은 당시 환경 이력이다.

실험 설계는 [run_guarded_development.py](../../experiments/archive/tools/run_guarded_development.py)에 있다. 기존 30건은 이전 Qwen 분석을 그대로 재생했다. 새 8건은 검증 코드 작성·검사 후 작성하고 Qwen이 새로 분석했다. 모델에 수동 정답/KG 후보를 주지 않았다. 동일 분석을 대상으로 ① 수정 전 조회 ② 연결절 수정만 적용한 조회 ③ 형태 근거 검증까지 적용한 조회를 저장해 효과를 분리했다. 번역은 ①/③의 두 조건을 이번에 모두 새로 실행했다. Qwen3.8-27B, 기존 기본 시스템 프롬프트, seed=20260923, temperature=.3/top_p=.8/top_k=20/max_tokens=512/thinking=false는 동일하다. 분석 호출은 이전 설정 temperature=0을 유지했다.

대표 출력과 남은 문제:

- DEV024 ‘도착할 때까지’를 조건 연결절로 분류한 분석 등은 여전히 의심스럽다. 후보가 도달 가능해진 것과 적합한 용법을 찾은 것을 구분해야 한다.

원문과 같은 표현은 표준어와 방언이 공유할 수 있으므로 동일 출력 수를 실패율로 쓰지 않는다. 높임 수치도 모든 어체의 적합성을 평가한 것이 아니다. 수동/자동 KG 출력은 21/30건 동일했고, 선택된 진술 ID 집합은 9/30건 달랐다. 수동 KG가 기본 출력보다 높임을 유지한 사례는 있지만 자동 분석 조건이 수동보다 개선됐다는 결론은 성립하지 않는다. 조건부 지식 외에 분석·보존 메모도 함께 제공했으므로 순수한 그래프 구조 효과를 분리한 대조도 아니다. 수동/자동 패킷의 style_policy 설명 문구도 다르며, 적용 정책 ID와 실제 목표 대안만 동일하다.

|---|---|

## 분석 규격 정합성 수정 — 2026-10-01

1단계는 **원문 분석값 → 검증 → 목표 조건 도출 → 기존 조회**의 입력 경계를 구현했다. 자동 분석기나 번역 품질 개선의 완료를 의미하지 않는다. 기존 30문장의 수동 분석 원본과 과거 조회·번역 결과는 보존했다. 아래 9월 29일 실행 구조 설명은 당시 상태이며, 입력 검증·높임 이중 입력에 관한 부분은 이 절로 갱신한다.

| 발견한 불일치 | 실제 수정 |
|---|---|
| `observed_politeness`와 `target_scenarios`를 따로 작성하여 서로 어긋날 수 있음 | 새 입력 버전 1.1은 목표 시나리오를 받지 않는다. 명시된 `development_politeness_preservation_v1` 정책에서 관찰 높임으로 조회 목표를 만든다. 기존 1.0 파일은 두 값이 일치할 때만 호환 변환한다. |
| DEV004/015/016의 `host_pos=copula`가 공통 규격에 없음 | `analysis_contract.json` 0.4에 계사 분석값을 등록하고 그래프를 다시 내보냈다. 다른 품사와 자동 등치하지 않으며 `host_class=nominal_copula`를 유지한다. 노드·관계 수는 6,092/15,639로 동일하다. |
| DEV006 `subject_honorific`, DEV013 `modality`가 미등록 KG 특징으로 전달됨 | 기존 값을 잃지 않고 `annotations`로 옮긴다. 설명 메모로 전달하며 조건 일치에 사용하지 않는다. `observed_subject_honorific` 및 `tense_or_modality`도 별도 관찰값으로 전달한다. 이를 새 문법 규칙으로 등록한 것은 아니다. |
| 잘못된 값·절 범위·중복 식별자가 조회에 들어갈 수 있음 | 그래프 접근 전에 항목/값/공급원/원문 범위/식별자 중복을 검사한다. 질문 해석과 비의문 유형의 명시적 충돌도 거부한다. 미확인 값은 적합 판정으로 바꾸지 않는다. |
| 규격에는 있지만 조회 경로가 없는 연결 관계가 사전 조회 오류를 일으킴 | 미구현/미확인 기능은 `analysis_gaps`에 이유를 기록하고 후보를 선택하지 않는다. 새 경로를 만든 것은 아니다. |

실제 규격·호환 변환·검증은 [analysis_input.py](../../experiments/analysis_input.py), 연결은 [run_manual_kg_development.py](../../experiments/run_manual_kg_development.py), 허용 KG 특징과 값은 [analysis_contract.json](../../grammar/analysis_contract.json)을 따른다. 입력 검증 코드는 공통 특징 규격을 직접 읽으므로 품사 등의 열거 값을 별도로 복제하지 않는다.

새 분석 인스턴스 1.1의 형식은 다음과 같다. 자동 분석기가 구현되면 이 형식으로 제출해야 한다.

| 위치 | 형식 및 의미 |
|---|---|
| 최상위 | `version: "1.1"`, `origin`, `status`, `policy`, `items`. 분석 출처와 개발/검증 상태를 숨기지 않는다. |
| `policy` | `style_policy_id: "development_politeness_preservation_v1"`; 기존 설명용 `style_policy`, `candidate_features`, `selection`; 지역 필터는 현재 미구현이므로 `target_region`은 생략 또는 null. |
| 문장 항목 | 고유 `id`, 원문 `input`, `preservation_note`, `unqueried_structure_note`, 하나 이상의 `clauses`. |
| 절 식별·결속 | 고유 `clause_id`와 `predicate_complex_id`, `role: main/connective`, 원문과 정확히 같은 `text`, `[start,end]` 문자 범위. 끝 위치는 미포함. 주절 범위에 연결절이 포함되는 현재 분석을 허용하며 완전한 구문 트리를 주장하지 않는다. |
| 관찰값 | `features`에는 공통 규격의 입력 특징만 넣는다. `observed_politeness`는 polite/non_polite/unknown 중 하나. 선택적인 `observed_subject_honorific`, `tense_or_modality`는 코드의 허용 관찰값을 따른다. |
| 후보 구성 가정 | `preserved_candidate_features`: preceding_form/following_form/prefinal_profile/attachment_coda/attachment_coda_class만 허용. 관찰값과 별개이며 아직 수동 가정이다. 후보 규칙에서 요구하는 값을 역으로 채우지 않는다. |
| 설명 메모 | 선택적인 `annotations.subject_honorific`, `annotations.modality`는 문자열 설명. 조회 조건이 아니며, 1.0에서 옮긴 두 메모의 원문 값도 여기 보존한다. |
| 미확인 | 선택 특징의 누락 또는 null은 미확인이다. 높임은 명시적으로 unknown을 쓴다. 미확인 높임은 목표를 추정하지 않아 전달 후보가 없다. 의미상 정확성 전체나 모든 모순을 검증하는 장치는 아니다. |

조회 목표 정책은 기존 실험의 가정을 명시적으로 재사용한다. polite → HAEYO_LEVEL, HAISOCHE, informal_high의 세 대안; non_polite → HAECHE, HAERACHE, informal_low의 세 대안이다. **각 어체가 동일한 높임·자연스러움을 가진다는 언어학적 결론은 아니다.** 입력에서 높임을 판별하는 작업은 여전히 수동이며, 주체 높임(-시-/계시다)과 청자 높임을 동일시하지 않는다. 실제 생성물의 높임 보존도 별도 검사가 필요하다.

[검증 산출물](../../experiments/archive/diagnostics/analysis_validation.results.json)에 30문장/38단위의 정규화된 분석, 입력·규격·코드 해시, 이번 수정 직전/직후의 선택 진술 ID 비교, 과거 파일 보존 확인을 기록했다. 비교 결과 후보가 달라진 문장은 0개다. 과거 Qwen 생성 실험과의 품질 비교가 아니라 **동일한 보완 KG에서 입력 경계를 바꾼 전후 비교**다. 신규 검사 9개는 잘못된 값, 높임 정책 충돌·미확인, 공급원 혼입, 중복 ID, 원문 범위 초과, 미구현 경로 등을 확인한다. 실험 코드 29개, 문법·조회 87개 및 빌드 재현 검사를 수행했다. Qwen 생성은 실행하지 않았다.

입력 검증만 다시 실행하려면 프로젝트 루트에서 `/usr/bin/python3 current_kg/experiments/run_manual_kg_development.py validate`를 사용한다. 이 명령은 위 검증 산출물을 현재 정규화 결과로 갱신하며, 이번 작업의 일회성 수정 전후 비교를 재실행하지는 않는다. `prepare`는 기존 조회 산출물을 덮어쓰므로 이번에는 실행하지 않았다. 이후 생성에서는 분석 경계 코드·규격·목표 정책의 해시도 검사하여 오래된 조회 결과의 재사용을 차단한다.

다음 단계는 이 형식을 출력하는 자동 입력 분석기 설계·검증이다. 시작 기능의 제한, 연결된 조건의 미확인 처리, 후보 6개 상한/정렬, 최종 번역 검증은 아직 남아 있다. 이번 규격 수정만으로 사투리 생성에 효과적이라고 결론내리지 않는다.

7종 전체를 절·표·각주 단위로 대조한다. 원문에서 기록으로 확인해 누락을 찾고, 기록에서 원문으로 되짚어 오해·과장·근거 없는 조건을 찾는다. 항목별로 원문 위치, 대응 기록·관계, 유지/보완/신규/배경/보류/제외 판정과 이유를 남긴다. 목록만 만들지 않고 누락 작성과 조건 보완을 함께 진행한다.

앞서 조현준 PDF 56–103쪽부터 전수 대조하는 계획을 제안했으나, 이후 사용자와 전수검수를 실험의 선행 조건으로 삼지 않고 제한된 점검과 개발 실험을 병행하는 방향으로 전환했다. 현재는 개발 입력의 실제 조회·출력에서 발견한 문제와 위험 항목을 중심으로 원문을 대조하며, 원문 전체 포괄을 주장하지 않는다. 문헌 간 연결은 양쪽 원문을 함께 확인하고 기능 공유·동일 용법 후보·활용 참조·충돌을 구별한다. 원문에 없는 조건은 공백으로 남긴다. 이번 폴더 정리는 전수 검수 수행이 아니다.

## 2026-09-23 같은 시드의 KG 예비 비교

사용자가 서버의 시드 지원 확인과 같은 시드의 KG 비교를 요청했다. **기존 시드 미지정 결과와 비교하지 않고**, KG 없는 조건도 다시 생성했다.

- 모델: 요청·모델 목록·응답 모두 Qwen3.8-27B. 실제 체크포인트·양자화·하드웨어는 미확인.
- 시드: 두 조건 모두 20260923. 동일 시스템 프롬프트·temperature 0.3·top_p 0.8·top_k 20·max_tokens 512·thinking false.
- 서버 확인: 숫자 seed 요청 성공, 잘못된 문자열 seed는 HTTP 400이며 오류에 seed 명시. 같은 입력·시드 2회 출력 일치. 완전 결정성 보장은 아님.
- 본 비교: 30입력 × prompt_only_seeded / kg_manual_seeded = 60출력, 모두 stop 종료. 매 요청은 독립이며 입력별 두 조건의 실행 순서를 번갈아 배치했다.
- KG 조건: Codex가 표준어 입력의 관련 기능·구성을 분석하고 시작 관계를 지정했다. 그래프에서 형태·조건·근거를 읽고, 변이 및 일부 문헌 간 연결을 따라 자료를 구성했다. 수동 분석 메모·정답 문장은 모델에 직접 제공하지 않았다. 단, 선택 자체에 연구자 판단이 들어가므로 자동 검색 성능으로 해석하지 않는다. 이전 기본 출력은 이미 본 상태였다.
- needs_review·example_only 및 미확인/불일치 조건은 제외했다. speech_level을 표준어 높임에서 임의 추론하지 않아 일부 의문 관계를 보류했다. unknown 처리·조건 노드 손실·통합 엣지 제거·연결 대상 재검토 상태 등의 새 구현 검사 6개 통과. 현행 KG 승인 상태는 변경하지 않았다.

### 어미 지식과 입력 연결에 대한 후속 확인

사용자는 원문에 어미 정보가 많은데 출력에 적용되지 않는 것은 연결 구축 문제인지 질문했다. 실제 저장본에서 H014(하이소체 문장 유형별 어미), H019(는교 품사 결합), H022(니더/이더 품사·말음 조건), Q001/Q002(나/노), J058(나/노와 시상 결합) 등을 확인했다. 어미 정보가 없다고 볼 수는 없다.

구체적인 연결 불일치: H014의 네 종결 기능과 H019·H022·H028의 어미 관계는 application.target이 predicate.construction으로 저장돼 있다. 기존 query_review는 realizes 관계 및 clause.final_ending 적용 대상만 받아 이들에 대한 접근이 제한된다. H019/H022처럼 attaches_to만 있는 기술은 기능 realizes 경로만으로 찾을 수 없다. kind=ending 95건 안의 관계 적용 대상은 predicate.construction 142개, clause.final_ending 58개, clause.connective 16개, predicate.inflection 2개, clause.question_interpretation 1개다. ending에는 연결어미 등도 있으므로 142개 전체를 오류로 판정하거나 일괄 치환하지 않는다.

이번 비교는 기존 query_review를 그대로 실행한 것이 아니라 수동으로 지정한 assertion 27종에서 패킷을 만들었다. 실제 패킷은 20개 기록만 사용했다. 따라서 기존 조회기의 필터 문제를 이번 출력의 직접 실행 원인으로 혼동하지 않는다. 이번 실행에서는 다른 후보를 충분히 탐색하지 않은 수동 선택과, 목표 말투 연결이 미정인 채 조건 미확인 후보를 제거한 것이 확인된 병목이다. 그래프의 기능·결합·높임 기술이 고르지 않다는 문제도 존재하지만 생성 결과만으로 KG 전체의 사실 오류나 단일 원인을 확정하지 않는다.

- 니더/이더: 설명 문자열 대신 품사와 후보의 실제 결합 지점 말음을 조건으로 저장했다. 사전형 어간 받침(stem_coda)과 후보 결합 지점 받침(attachment_coda)을 구분한다. H023의 맑다·궁금하다·좋다·낫다 관찰형을 어휘·품사 조건으로 정리하고, 맑다/궁금하다의 니더 배제를 새 진술 A7로 추가했다. 이 정규화는 extractor_interpretation이며 원문 14쪽의 예외 목록에 근거한다.
- 의문형+요/예: following_form은 후보 내부, sentence_type/question_type은 입력, speech_level은 목표 정책으로 구분했다. 결합 후 높임은 HAEYO_LEVEL로 구분하며 기저형의 HAGECHE를 상속하지 않는다. 19쪽의 판정/설명 구분과 34쪽 결합 설명을 연결한 해석임을 표시했다.
- 나/노·가/고: 기존에 구조화된 질문 유형·서술부·선어말 조건은 유지하고 값의 공급원을 명시했다. 기본형 Q003~Q005에서 변경형 Q006과 원문 충돌 Q007로 이동하는 관계를 추가했다. Q007의 needs_review 및 보류 연결 상태를 유지한다.

수정 원본은 authored JSON, 값 공급원 규격은 record.schema.json/analysis_contract.json, 기록 간 관계와 범위·진단 입력은 integration.json의 condition_exception_review에 있다. 평면적인 입력값만 받던 기존 조회/패킷 코드도 새 공급원 정보를 무시하지 않도록 수정했다. 자동 입력 분석·일반 후보 선택·생성은 아직 연결하지 않았다.

### 전체 어미 범위로 확대 — 2026-09-28

작업 범위는 기존 어미 직접 관련 185건과 보조 89건, 합계 274건이다. 개발용 30문장의 정답 어미에 한정하지 않는다. [작성검토.md](../../grammar/작성검토.md)의 기존 전체 목록에 각 기록의 남은 작업을 추가했다. JSON의 `ending_connections.records[].condition_work`에는 설명형 조건과 값 공급원이 미확정인 진술 ID, 다음 작업, 예외 포괄성 미확정 상태가 있다. 연결 부재를 곧바로 오류나 예외 없음으로 판정하지 않는다.

이번에는 추가 38건을 원문과 대조해 조건을 수정했다. 니더·니껴/니꺼의 선어말 결합, 이더/리더·계사 시더/동사 ㄹ시더, 이소·소·세·이시더/시더, 도가/도고/다고·온나·래, 거로의 의도/금지를 다뤘다. 청자만 행동하는 명령과 공동 행동을 제안하는 청유, 주어 인칭과 의도의 주체, 요청의 수혜자를 구별한다. 요청은 `REQUEST` 기능에서 접근하며 문장 형식을 무조건 명령으로 간주하지 않는다. 함양 자료의 명령·청유·평서·감탄은 문헌상 대우 정도를 목표 조건으로 구분하고, 연결어미는 조건·원인·양보·이동 목적 등을 절 관계로 나눴다. 서부 하소체 요/소는 모음·ㄹ·기타 자음의 실제 결합 조건을 구별하며, 고/꼬·느는고는 상대 응답 요구와 자문을 구분한다. 문헌 간 이더 분포 차이는 보류 연결, 시더의 존재사 허용 각주는 별도 관찰로 보존한다.

별도로 기존 조건의 의미상 공급원이 명확한 518개 관계에 입력(input)·선택할 구성(candidate)·목표 설정(target)을 명시했다. 이 숫자는 원문 재검토나 조건 구조화 완료 건수가 아니다. 어휘·어간처럼 값의 기준을 더 확인해야 하는 항목은 자동 추정하지 않았다. 조건·예외/활용/대조 연결은 17개 추가했다. 기존 진술과 표현 ID는 유지했다.

**실제 단계 — 실행 순서**

1. JSON 로드 및 노드/간선 인덱스 생성. 전체 KG를 메모리에 읽는다. 현재 후보 탐색은 매 단위 전체 간선 목록을 훑는다.
2. span/text 일치 검사. features 안의 speech_level은 입력 관찰과 목표 말투 혼동으로 오류 처리한다. 전체 입력 스키마 검증은 아니다.
3. 위 11개 중 기능 집합 및 종결/연결 적용 위치를 선택한다. 다른 적용 위치를 시작점으로 생성하는 코드는 없다.
4. 표현 용법 → realizes → 선택된 기능인 간선을 찾는다. function에서 realizes를 역으로 찾는 절차다. 단순 about/classified_under는 후보 발견 경로가 아니다.
5. 해당 간선의 assertion_id를 읽어 진술의 적용 위치·조건을 확인한다. 후보 자체 구성은 preserved_candidate_features 복사본으로 시작한다.
6. 요/예 결합형에 한해 후보를 대상으로 하는 has_surface_form을 역탐색하고 그 기저형의 combines_with를 찾아 요/예 성분이 단 하나이면 following_form을 채운다. 일반 활용 생성이나 모든 결합 경로 탐색이 아니다.
7. 모든 target_scenarios를 각각 대조한다. 같은 표현 용법을 주어로 가진 진술들을 확인한다. 현재 진술의 application.feature_sources에 따라 input/candidate/target의 필드를 읽고, 공급원이 없는 과거 진술은 input 평면값만 본다.
8. requires_all/requires_any 조건 노드와 진술 속성이 동일한지 검사한다. 값은 문자열만 판별하고 is/one_of만 지원한다. 누락/문자열 외 값/미지원 연산자는 unknown. all 중 mismatch 또는 비어 있지 않은 any 전부 mismatch이면 mismatch; 그 외 미해결 조건이 남으면 unknown; 충족하면 match.
9. 시작 표현 용법 및 그 용법 자체의 진술에서 아래 다섯 통합 관계만 정방향 한 단계 따라간다. 연결된 끝점이 진술이면 해당 진술 하나, 표현 용법이면 그 용법을 주어로 하는 진술 모두를 읽는다. 그 끝점에서 다시 통합 관계를 재귀 탐색하지 않는다.
10. 아래 제외 기준을 모두 적용한다. 연결 지식의 조건을 기본 용법에 무조건 상속하지 않는다.
11. 하나라도 통과한 목표 시나리오가 있으면 목록에서 첫 통과 시나리오를 선택한다. 조건 수(all+any 항목 수) 내림차순, 진술 ID 오름차순으로 정렬한다. (표현 문자열, 기록 ID) 단위로 중복 제거하고 최대 6개를 남긴다. 다른 기록의 같은 표현은 중복으로 제거되지 않는다.
12. 후보·조건·범위·근거·설명·공백·추가 참조를 JSON 참고 패킷으로 구성해 Qwen user 메시지에 넣는다. 원래 표준어 전체도 함께 제공한다. 후보가 0개여도 공백 안내를 주고 생성할 수 있다. Qwen 내부에서 후보를 실제 사용했는지는 확인하지 못한다.

### 문헌→KG 구조화 감사 — 2026-09-29

**결론:** 작성본을 그래프로 내보내는 과정의 손상은 발견하지 못했다. 그러나 문헌 정보를 실행 가능한 용법·조건으로 표현하는 단계에서 중요한 연결 누락과 조건 표현의 결함을 확인했다. 현재 KG를 ‘입력에 맞는 방언형과 제약을 충분히 판별하는 완성된 규칙 체계’로 취급하면 안 된다. 이 결론은 개별 개발 문장에 맞춘 어미 추가가 아니라 원문→작성본→그래프 구조 대조에 근거한다. KG 전체가 거짓이거나 버려야 한다는 결론은 아니다.

**처음부터 어디가 어긋났는가에 대한 판단:** 보존용 문헌 기록과 실행 가능한 문법 규칙을 동일한 수준으로 취급하기 쉬운 구조가 남아 있다. schema는 조건 필드와 근거 참조의 존재를 검사하지만, 그 값이 실제 입력에서 판별 가능한 문법 특징인지, 원문 표의 각 항목·예외가 빠짐없이 작성됐는지는 검사하지 않는다. 여기에 기능 연결을 추가했어도 같은 용법의 높임·활용·예외가 함께 실행되도록 연결되었는지 별도 검증이 필요하다. 이는 기록과 코드에 근거한 설계 진단이며 과거 작성자의 의도에 대한 추정이나 모든 번역 오류의 인과 설명은 아니다.

**검증과 다음 단계:** `/usr/bin/python3 current_kg/grammar/build.py check`로 331건의 작성본에서 현행 산출물이 재현됨을 확인했다. 감사에서 중복 ID·끊어진 끝점·조건 노드 불일치·진술 연결 오류·고립 노드는 모두 0이었다. 이 결과는 언어학적 완전성 검사가 아니다. 다음 조회 구조 감사에서는 S01~S05가 어떤 경로에서 누락·과잉 허용을 만드는지 확인하고 공통 표현 규약의 수정 범위를 정한다. 특정 30문장의 정답 어미를 추가하는 방식으로 수정하지 않는다. 새 문장 일반화 검증과 모델 출력의 의미·높임 보존 검증은 아직 남아 있다.


### 30문장별 실제 KG 조회 경로와 높임 처리 — 2026-09-28

아래는 저장된 조회 기록과 실제 Qwen 요청을 대조한 기록이다. 새 생성이나 결과 수정은 하지 않았다. 기능 노드에서 `realizes` 관계를 역방향으로 찾아 표현 용법을 찾고, 그 관계에 지정된 진술의 조건을 평가했다. `F`는 표현 용법 노드, `A`는 조건·근거를 담은 진술 노드다. 따라서 기능 → 용법 → 진술이라는 표시는 조회 절차이며 모두 같은 방향의 그래프 간선이라는 뜻은 아니다. Qwen이 내부적으로 어떤 후보를 사용했는지는 이 기록으로 확정할 수 없다.

이번 높임 구분은 `observed_politeness`에 수동으로 기록했고, 조회에는 별도로 작성한 `target_scenarios`를 사용했다. 존댓말·반말을 자동으로 판별하거나 그 값에서 목표 시나리오를 자동 생성한 실행이 아니다. 종결 용법은 `speech_level` 또는 `addressee_treatment` 조건을 요구하지만, 연결어미에 청자 높임을 일괄 요구하지는 않는다.

사용자 지정 방향: 목표는 원문의 의미·높임을 유지하는 자연스러운 경상도 방언이다. 부산·경산·포항 등 세부 지역을 입력에서 추정하거나 필수 지정하게 하지 않는다. 자료의 지역 출처는 근거로 보존하되, 특정 지역을 지정하지 않았다는 이유만으로 후보를 막는 정책을 요구하지 않는다. 이 문단은 앞으로의 설계 기준이며, 과거 실험 프롬프트나 실행 정책을 소급해서 바꾼 것은 아니다.

전체 발견 후보와 보류·제외 사유는 [조회 원본](../../experiments/archive/legacy_development/development_30.manual_retrieval.json)의 `items → clauses → candidates → scenarios`에 있다. 아래에는 그중 실제 전달한 후보의 경로·조건과 추가 참조 진술을 모두 표시한다. 조건의 match는 등록된 조건의 일치를 뜻하며, 문장 전체의 자연스러움 인증이 아니다.
